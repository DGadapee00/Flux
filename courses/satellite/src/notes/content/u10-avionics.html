Part I

The onboard computer

1The computer and its buses

Command and data handling is the craft's nervous system. One computer takes commands from the ground, runs every subsystem's software, gathers telemetry and stores the payload's data.

Key idea
  • The processor runs the flight software. Its speed must cover the busiest moment, with margin.
  • Memory comes in kinds: read-only memory for the boot image, RAM for the running software, flash for stored data. Flash and RAM take upsets, so they carry a code and a scrubber (Unit 9).
  • Buses join the computer to sensors, radios and the payload. Small craft use embedded buses: I²C and SPI inside a board, RS-422 and CAN between boards, SpaceWire for fast data.
  • A watchdog resets the computer if the software stops answering.

Choose a bus by the rate it must carry. I²C shares two wires among many devices at 100 or 400 kbit/s, with a 3.4 Mbit/s mode on newer parts. SPI moves one bit per clock on its own lines, about 20 Mbit/s at a 20 MHz clock.

Worked example · a camera on the bus

A camera makes 2048 × 2048 pixels of 12 bits every 10 s:

\[ \frac{2048^2 \times 12\ \text{bit}}{10\ \text{s}} = 5.03\ \text{Mbit/s}. \]

That is 12.6 times what fast-mode I²C carries, and more than its 3.4 Mbit/s mode. A 20 MHz SPI link carries it with room to spare. The magnetometer, at a few hundred bits a second, can share an I²C bus with the temperature sensors.

Common mistake

Sizing the bus for the average rate when the device sends in bursts. A camera that dumps a frame in one second needs ten times its average rate while it does.

2Flight software and scheduling

Flight software is a set of tasks that repeat: attitude control ten times a second, commands, payload processing, telemetry, housekeeping. Each must finish before it runs again.

Derivation

Task \(i\) runs for \(C_i\) every period \(T_i\). The processor's load is

\[ U = \sum_i \frac{C_i}{T_i}. \]

Under rate-monotonic scheduling the task with the shortest period has the highest priority and interrupts the rest. Liu and Layland showed that every deadline is met if \(U \le n(2^{1/n} - 1)\): 0.828 for two tasks, 0.743 for five, toward \(\ln 2 = 0.693\) for many. That is a safe test, not a limit.

The exact test finds each task's worst response. It comes when every task is released together, and it is the smallest \(R_i\) with

\[ R_i = C_i + \sum_{j < i} \left\lceil \frac{R_i}{T_j} \right\rceil C_j , \]

the task's own run plus every higher task's runs that start before it finishes. The task is on time if \(R_i \le T_i\). The lab finds \(R_i\) by iterating this from \(R_i = C_i\), and checks it against a run of the scheduler itself.

Worked example · the baseline processor

Attitude control takes 18 ms every 100 ms, commands 20 every 250, payload processing 90 every 500, telemetry 120 every 1000, housekeeping 150 every 2000. The load is

\[ U = 0.18 + 0.08 + 0.18 + 0.12 + 0.075 = 0.635, \]

under the 0.743 bound. Housekeeping, the lowest priority, finishes 490 ms after its release in the worst case.

Worked example · a processor two-thirds as fast

Every run takes 1.5 times as long and the load is 0.953, past the bound. The exact test still passes: housekeeping's worst response is 1878 ms against its 2000 ms period. Twenty more milliseconds of payload processing at baseline speed take the load past 1, and then no schedule can fit.

Common mistake

Reading the bound as a limit, or ignoring tasks that share data. When a low task holds a lock a high task needs, a middle task can block both. Mars Pathfinder reset itself repeatedly in 1997 for that reason, until priority inheritance was switched on from Earth.

3Faults, watchdogs and safe mode

A craft out of contact for hours must notice its own faults and keep itself alive until the ground can help.

Key idea

Fault management has three steps: detect that something is wrong, isolate which part, and recover. The simplest tools are a watchdog, which resets a computer that stops answering, and limit checks on telemetry. The last line is safe mode: point the arrays at the Sun, shed loads, keep the radio listening and wait for the ground.

Rule-based fault management lists each fault and its response, and misses what nobody listed. Model-based fault management reasons from a model of how the craft should behave, so it can handle combinations nobody wrote down.

Worked example · a watchdog's timing

The software must reset the watchdog every second; the watchdog resets the computer if 4 s pass without one. A task that hangs is caught within 4 s. The timeout must be longer than the longest normal gap, such as a flash write that blocks for 1.5 s, or the watchdog resets a healthy computer.

Common mistake

A safe mode that needs the part that failed. If safe mode points the arrays using the star tracker, a failed tracker leaves the craft unable to find the Sun. Safe mode should use the simplest, hardiest sensors: coarse Sun sensors and a magnetometer.

4Building flight software

Flight software is often the part that runs late. Its size is hard to estimate and its faults show up at integration.

Key idea

Most small craft build on a framework, such as NASA's Core Flight System or F Prime, over a real-time operating system. The framework gives command handling, telemetry, timing and messaging; the mission writes the control laws and the payload's processing.

Software grows. MIT 16.851 advises sizing the computer at four times the estimated need at the requirements review, and keeping a full 100% margin at launch: no more than half the processor and half the memory in use.

Worked example · the margin rule

At the requirements review the software is estimated to load a candidate processor to 30%. Four times the estimate is 120%: this processor is too small. One twice as fast puts the estimate at 15% and four times it at 60%, which fits. If the delivered software later loads it to 45%, the launch margin, at most 50%, still holds.

Common mistake

Testing the software only on a desktop. Test it on the flight computer, with the flight timing, sensors and buses, or with hardware that stands in for them: test as you fly.

5The data budget

The data budget asks whether the passes can send down everything the craft records, and how big the store must be between passes.

Derivation

An overhead pass above elevation \(\varepsilon\) lasts (Unit 1)

\[ t_p = T\,\frac{\lambda}{\pi}, \qquad \lambda = \arccos\!\left(\frac{R}{r}\cos\varepsilon\right) - \varepsilon . \]

A mid-latitude station sees a low craft in two groups of passes a day, twelve hours apart, each on \(k\) consecutive orbits. With a radio sending \(D\) and the craft recording \(g\) on average,

\[ \text{made} = 86\,400\,g, \qquad \text{sent} = 2k\,t_p\,D . \]

If more can be sent than is made, the store empties in each group of passes and peaks just before the group's first pass, after the long gap. If not, it grows by made − sent every day until it is full.

Worked example · S-band, three passes a group

At 500 km, \(T = 94.5\) min. Above 10°, \(\lambda = 0.245\) rad and an overhead pass lasts 7.38 min. Six passes a day give 44.3 minutes of sending. At 1 Mbit/s that is 2.66 Gbit a day. The craft records 25 kbit/s of payload data and 2 of housekeeping, 2.33 Gbit a day: a 13.8% margin. The store peaks at 106 MB before each group.

Worked example · a 30° mask

If trees and buildings hide the sky below 30°, \(\lambda = 0.115\) rad and an overhead pass lasts only 3.45 min. The day's sending falls to 1.24 Gbit, short of the 2.33 Gbit recorded, and the store grows 136 MB a day.

Common mistake

Fixing a budget that does not close with a bigger store. The store fills a little more each day whatever its size; a larger one only takes longer. Record less, send faster, or add passes.

7Build it

Show the computer, the software and the downlink keep up with the mission.

Method

  1. List every device on the computer with the rate it sends, and give each a bus that carries its peak.
  2. List the flight software tasks with their periods and run times on the flight processor.
  3. Find the load and each task's worst response; keep the load at launch under half.
  4. Write the fault responses: what each limit check does, the watchdog's timeout, and what safe mode needs.
  5. Count the data a day against what the passes can send, and size the store for the longest gap.

What to produce

A block diagram with buses and rates, a task table with response times, a fault response table, and a data budget.

Handoff to other subsystems

Give Power the computer's draw. Give Communications the daily data volume and the rate needed. Give Mission and requirements the load and memory margins.

Review checklist

  • Every bus carries its device's peak rate.
  • Every task meets its deadline, and the load leaves a 100% margin.
  • The watchdog timeout is longer than the longest normal gap.
  • Safe mode does not depend on the part most likely to fail.
  • The passes send more than the craft records each day, with margin.
Worked example · build review

For your craft, list the tasks and find the load; check the slowest task's worst response; count the data a day against your passes and radio; size the store.

Use the checklist above to review the result. State each assumption and the evidence supporting each interface value.
